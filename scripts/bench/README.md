# Методика нагрузочного тестирования

Замеры снимаются **с двух сторон одновременно**: клиент гонит трафик через туннель,
сервер в это время пишет свою утилизацию. Так цифры клиента и нагрузка сервера
ложатся на одну временную шкалу.

## Схема стенда

```
 [ клиент бенчмарка ]  --VLESS+Reality-->  [ VPS: reality-xray ]  --freedom-->  [ интернет ]
   client-bench.sh          443/tcp              server-monitor.sh
   (SOCKS5 :10808)                               (docker stats)
```

Клиент бенчмарка — это **не** грейдер из РФ, а отдельная машина, с которой удобно
мерить: своя рабочая станция или (честнее по восходящему каналу) второй дешёвый VPS
в том же регионе. Важно: канал самого клиента не должен быть узким местом — иначе
меряется он, а не туннель.

## Что меряем

| Метрика | Как | Инструмент |
|---|---|---|
| Пропускная способность | скачивание фикс. объёма, direct vs tunnel | `curl -w %{speed_download}` через SOCKS5 |
| Задержка | time_total до лёгкого эндпоинта, min/avg/max | `curl -w %{time_total}` |
| Масштабирование | N параллельных потоков: 1→128, суммарный throughput и доля успешных | параллельные `curl` |
| CPU / RAM сервера | семплинг раз в секунду во время нагрузки | `docker stats` + `/proc/loadavg` |

> ICMP-ping через SOCKS не ходит, поэтому задержка меряется по TCP/HTTP (connect + TTFB),
> что ближе к реальному пользовательскому опыту, чем голый ICMP.

## Как запускать

**Терминал 1 — на сервере (VPS):**
```bash
./scripts/bench/server-monitor.sh 180        # писать 180 секунд
```

**Терминал 2 — на клиенте (нужен тот же .env, что сгенерировал сервер):**
```bash
# быстрая проверка живости туннеля:
./scripts/bench/client-bench.sh --smoke
# полный бенч:
./scripts/bench/client-bench.sh
```

Перенести `.env` на клиент можно так (секрет — обращайся аккуратно):
```bash
scp root@<SERVER_IP>:/path/testexss/.env ./.env
```

## Параметры (переопределяются через окружение)

```bash
THROUGHPUT_BYTES=104857600 \   # объём одиночного замера (здесь 100 MiB)
STREAM_BYTES=10485760 \        # объём на один поток в sweep (здесь 10 MiB)
CONCURRENCY_LEVELS="1 8 32 128 256" \
LAT_SAMPLES=50 \
XRAY_PLATFORM=linux/arm64 \    # если локальный кэш образа чужой arch (иначе QEMU занизит цифры)
./scripts/bench/client-bench.sh
```

**Грабли узкого клиентского канала.** Каждый поток в sweep идёт с `curl --max-time 120`.
На узком канале при большом числе потоков каждому достаётся малая доля полосы, и поток
не успевает скачать `STREAM_BYTES` за 120 с — в таблице это выглядит как `fail`, хотя
туннель исправен. Считать так: `STREAM_BYTES * 8 * потоки / полоса_бит_с` должно быть
заметно меньше 120 с. Для канала ~50 Мбит/с и 64 потоков `STREAM_BYTES=2097152` (2 MiB)
— рабочее значение.

## Выход

- `bench/out/latency-*.csv` — все сэмплы задержки (direct/tunnel)
- `bench/out/concurrency-*.csv` — throughput и успешность по уровням параллелизма
- `bench/out/server-*.csv` — **сырые** счётчики сервера по секундам: `ts_ms`,
  `cpu_usec` (cgroup v2), `cpu_ticks` (`/proc/<pid>/stat`), `mem_bytes`, `rx_bytes`,
  `tx_bytes`, `load1`. Проценты и Мбит/с считает сводка монитора по дельтам соседних
  строк — сырьё можно пересчитать заново в любой момент.

Монитор запускать так, чтобы управление вернулось сразу, иначе его окно истечёт до
начала нагрузки и в CSV будет простой:

```bash
ssh -f user@server 'cd ~/testexss && ./scripts/bench/server-monitor.sh 200 1 bench/out/server-run.csv > /tmp/mon.log 2>&1'
# затем СРАЗУ на клиенте: ./scripts/bench/client-bench.sh
# после прогона сверить, что окно накрыло бенч: первый и последний ts_ms в CSV
```

CPU% в `docker stats` считается относительно **всех** ядер: 100% = одно полное ядро,
на 2-ядерном сервере потолок 200%.
